## 1. 背景：E1 一晚上训练暴露的问题

实测（7.6h，8/60 代，RTX 5060 Ti）：
- 单代 ≈ 1 小时，跑满 60 代 ≈ 60 小时；GPU 占用 13%，CPU 单核满。
- 逐步阻塞：每手为一个可观测单位，慢、且不可"看着跑"。

仅此两项就把训练环境划成两问：
**① 吞吐量** —— 为什么这么慢，怎么才能快到"预算内能迭代一轮实验"。
**② 可观测性** —— 训练中怎么"看见"在发生什么，别靠 60h 后再被动开图。

---

## 2. 问题一：吞吐量
### 2.1 时间花在哪（先测量，再动刀）
~2.3ms/手的开销分层（量级估计，待 profile 证实）：
1. **逐步 GPU↔CPU 往返**：`select_action` 每手 `obs→cuda→前向→detach→cpu→argmax`，
   两次同步；小 CNN 单样本推理本身亚毫秒，同步往返才是大头。**CPU 上跑推理可能反而
   更快**（省同步）——一个便宜且可能高收益的点。
2. **Minimax 对手的纯 Python 搜索**：B2 池一半局的白方是 minimax-easy，每手一次搜索。
   隐性 CPU 大头，**占比待 profile 证实**。
3. **状态表示每手重建**：`observation()` 每手重建双平面、`valid_moves()` 每手扫 225 格。

### 2.2 结构性解法：并行环境 / 批处理自弈
唯一能再上台阶的路：同时步进 K 个环境，K 个黑方状态拼一个 batch 一次前向，
批量合法 mask 出动作，共享一个 replay buffer。逐手 Python/GPU 固定开销摊到一批。

### 2.3 决策建议
不要拍脑袋决定上不上批处理。**先 profile（cProfile/分段计时）**，量出 180ms/局里
minimax 占多少、Python 循环占多少、GPU 同步占多少——测量 > 猜。
- minimax 占比高 → 最大赢家是砍它的成本，未必重构并行。
- 确认是逐手同步 + Python 循环 → 才值得上并行环境。

## 3. 问题二：可观测性
### 3.1 现状痛点
- stdout 全程静默，只按代写一行 jsonl；曲线 PNG 等 60 代结束才出。
- 崩溃无恢复；无吞吐/资源读数；没有"卡死 vs 慢"的判别手段。

### 3.2 提升意见（优先级排序）
1. **逐行实时日志**：每代一行 `era·steps·loss·entropy·eps·win_*` + **episodes/sec + 预计剩余时长**。
2. **代内增量**：每 1k 局一条轻量采样，1h 的"代"里时刻能看到在动。
3. **每代自动刷曲线 PNG**：curve.png 每代覆盖，训练中可打开看形状。
4. **资源仪表盘**：顺带记 GPU/CPU 利用率（13% GPU"饿死"不该靠肉眼发现）。
5. **可恢复训练**：定期 checkpoint + resume 续训，崩溃不白跑。

## 4. 范围界定（用户拍板）
- ✅ 本轮做：吞吐量、可观测性（环境层地基）。
- ❌ 本轮不做：数值不稳定（Q 爆炸/loss 1e22/entropy -0.0）、信号密度（~78 手只有 1 个终局 ±1）、
  难度曲线（50% minimax-easy 冷启动纯负信号）。这三个是"训练问题"，单独再议。

## 5. 带问题去参考项目（consult 清单）
读参考项目时逐条核对，回来补进本节。每个项目标出：做法 / 是否可借鉴 / 代价。

**吞吐：**
- 它们如何并行步进多环境？是按 batch 合成单前向，还是进程/线程池？
- 推理放 CPU 还是 GPU？同步开销怎么消？有没有"环境在 CPU、网络在 GPU"的异步架构？
- 合法性 mask 在 batch 里怎么表达？每环境步数不一（局长不一）如何处理？
- minimax/启发式对手在多环境里是 CPU 并行还是概率化裁剪？还是干脆弃用手写搜索、换成更快的脚本对手？
- 增量维护状态（双平面 + valid_moves）还是每步全建？缓存策略？

**可观测：**
- 训练日志用什么格式/频率？有没有统一的行级采样？
- 曲线/进度怎么实时刷？文本终端、还是 web 面板？
- checkpoint / resume 的标准姿势？（含中间 checkpoint 频率）
- 有没有吞吐/资源埋点，跑得多快一目了然？
